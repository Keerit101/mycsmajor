Big O without a maths degree

Big O answers one question: when the input gets big, does this code get slow? You can answer it by counting, and the counting is easier than the notation suggests.

Count the work

Take the slowest-looking part of a function and count how many times it runs for an input of size n.

def total(nums):
    result = 0           # runs once
    for n in nums:       # runs n times
        result += n      # runs n times
    return result        # runs once

That is 2n + 2 steps. Big O throws away two things: constant factors and lower-order terms. So this is O(n), said "order n" or "linear time".

Throwing them away is not laziness. A constant factor depends on your language, your machine and the compiler's mood. The shape of the growth does not: double the input and linear code takes twice as long, whatever hardware you run it on.

The gap between the rows is the whole subject. An O(n²) solution to a 1,000-item problem does a million units of work; the O(n log n) one does ten thousand. That is the difference between a page that loads and a page that times out.

Nested loops multiply

def has_duplicate(nums):
    for i in range(len(nums)):          # n times
        for j in range(i + 1, len(nums)):   # up to n times each
            if nums[i] == nums[j]:
                return True
    return False

The inner loop runs n-1 times, then n-2, and so on, which totals n(n-1)/2. Multiply out and you get n²/2 - n/2. Drop the constant and the smaller term: O(n²). Halving the work does not change the shape.

Now the same job with a set:

def has_duplicate(nums):
    seen = set()
    for n in nums:              # n times
        if n in seen:           # O(1) on a set
            return True
        seen.add(n)             # O(1)
    return False

O(n), at the cost of O(n) extra memory. Trading memory for time like this is the most common move in the whole book, and chapter 5 explains why a set lookup is constant time.

Sequential code adds

def report(nums):
    nums = sorted(nums)          # O(n log n)
    biggest = nums[-1]           # O(1)
    for n in nums:               # O(n)
        print(n)

Add them: O(n log n) + O(1) + O(n). The largest term wins, so the whole function is O(n log n). One loop after another is addition; one loop inside another is multiplication.

Best, worst and average

Unless someone says otherwise, Big O means the worst case: the input that makes your code do the most work.

def find(nums, target):
    for i, n in enumerate(nums):
        if n == target:
            return i
    return -1

Best case the target is first, O(1). Worst case it is last or missing, O(n). Average, with the target somewhere random, is n/2 steps, which is still O(n). Say "linear" and you are right in both of the cases that matter.

You will also meet amortised cost. Appending to a Python list is O(1) amortised: usually it just writes into spare space, and occasionally it copies the whole list into a bigger block. Spread the occasional expensive copy over all the cheap appends and the average is constant.

Space complexity, in one paragraph

Count the extra memory the same way, ignoring the input itself. The first has_duplicate used O(1) extra space; the set version uses O(n). Recursion costs space too: each pending call keeps a frame on the stack, so a recursion n deep is O(n) space even if it allocates nothing.

The measurement that proves it

Theory is checkable. Searching a list of a million items scans from the start; searching a set hashes straight to the answer:

import timeit

big = list(range(1_000_000))
s = set(big)

print(timeit.timeit("999_999 in big", globals=globals(), number=100) / 100)
print(timeit.timeit("999_999 in s",   globals=globals(), number=100_000) / 100_000)

On the machine these pages were written on, the list took about 5 milliseconds per lookup and the set about 22 nanoseconds: roughly two hundred thousand times faster. Your numbers will differ; the ratio will not change much, and it grows as the data grows. That is Big O being right.

Measuring matters because Big O hides constants. For twenty items a "slow" O(n²) algorithm often beats a "fast" O(n log n) one, which is exactly why real sort implementations switch to insertion sort on small chunks. Reason with Big O; confirm with a timer.

Exercises

1. Name the complexity

Give the time complexity of each, in terms of n = len(nums).

# (a)
for n in nums:
    for m in nums:
        print(n, m)

# (b)
i = len(nums)
while i > 1:
    i = i // 2

# (c)
for n in nums:
    if n in nums[5:]:
        print(n)
Show answer

(a) O(n²). Both loops run n times, and they are nested.

(b) O(log n). Halving repeatedly reaches 1 after about log₂n steps. Any time a loop divides by a constant rather than subtracting, think logarithm.

(c) O(n²), and worse than it looks. in on a list is O(n), and nums[5:] copies the list on every iteration, which is another O(n). Slicing inside a loop is a quiet way to turn linear code quadratic.

2. Fix the quadratic

This counts how many items of a also appear in b. Make it linear.

def shared(a, b):
    count = 0
    for x in a:
        if x in b:      # b is a list
            count += 1
    return count
Show answer 
def shared(a, b):
    lookup = set(b)              # O(len(b)) once
    return sum(1 for x in a if x in lookup)   # O(len(a)) lookups at O(1)

The original is O(len(a) × len(b)) because x in b scans the whole list every time. Building the set costs one pass and makes every test constant. With two lists of 10,000 items that is 100 million comparisons down to 20,000.

One caveat worth remembering: a set drops duplicates, so if b can contain repeats and you need to count them, use collections.Counter instead.

3. Prove it with a timer

Time has_duplicate in both versions on lists of 1,000, 2,000 and 4,000 distinct numbers. What happens to each time as the input doubles?

Show answer 
import timeit

for n in (1_000, 2_000, 4_000):
    data = list(range(n))        # no duplicates: the worst case for both
    slow = timeit.timeit(lambda: has_duplicate_slow(data), number=1)
    fast = timeit.timeit(lambda: has_duplicate_fast(data), number=1)
    print(n, round(slow, 4), round(fast, 6))

The nested-loop version roughly quadruples each time you double n, because 2² = 4. The set version roughly doubles. Plotting those two lines is the most convincing explanation of Big O there is, and it only takes a minute.

Use a worst case on purpose. With duplicates near the front, both versions return almost immediately and the test proves nothing.
