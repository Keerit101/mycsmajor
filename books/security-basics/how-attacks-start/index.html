Security basics for programmers · Chapter 1

How attacks actually start

Almost every breach you read about began with input someone trusted. This chapter teaches you to find the places your own code trusts, which is the skill every later chapter builds on.

Nobody picks a lock they can walk around

Real attacks are rarely clever. They are usually one of these:

  • Software that was never updated, with a public exploit available.
  • Input that was used as instructions instead of being treated as data.
  • A credential that leaked, was reused, or was never changed from the default.
  • A check that happened in the browser instead of on the server.
  • A dependency nobody looked at.

You can see this for yourself. Scroll the Cyber Brief on this site, which lists the vulnerabilities being actively exploited each month, straight from CISA's catalogue. Most entries are command injection, path traversal, authentication bypass or a memory bug. The same handful of mistakes, in different products, every single month.

That is good news for a student. You do not have to learn everything. You have to learn these.

Trust boundaries

A trust boundary is any line where data moves from somewhere you do not control to somewhere you do. At that line, data is guilty until proven innocent.

In a small web application the boundaries are:

  browser ─────▶ your server        form fields, URL parameters, headers,
                                    cookies, uploaded files, JSON bodies

  internet ────▶ your server        anything fetched from another API

  your server ─▶ the database       values put into queries

  your server ─▶ the shell          arguments passed to other programs

  your server ─▶ the browser        values written back into HTML

  disk / env ──▶ your program       config files, environment variables

Notice that the boundaries point both ways. Data coming in needs validating. Data going out needs encoding for wherever it lands: quoting for SQL, escaping for HTML, argument lists for the shell. Most vulnerability classes in this book are one of those two steps missing.

The browser is not part of your program

This deserves its own line. JavaScript validation, disabled buttons, hidden fields and maxlength are user-interface features, not security. Anyone can open developer tools, or skip the page entirely:

curl -X POST https://example.com/api/order \
  -H "Content-Type: application/json" \
  -d '{"item": 7, "quantity": -5, "price": 0}'

If your server accepts a negative quantity because the form would never send one, you have a bug, and someone will find it. Every check that matters happens on the server. Client-side checks exist to be helpful, not to be trusted.

Attack surface

Your attack surface is everything an attacker can reach: every route, every parameter, every port, every file upload, every dependency, every admin page, every API key in a config file. The practical advice is simply to make it smaller.

  • Delete routes you no longer use, especially debug and test endpoints.
  • Turn off debug mode in anything public. A stack trace tells an attacker your framework, version, file paths and sometimes your database schema.
  • Do not install a package to do something a few lines can do.
  • Do not expose a database, a Redis instance or an admin panel to the internet.
  • Give each account, service and key the smallest permissions it can work with. This is least privilege, and it is what turns a break-in into a contained one.

Thinking like the person testing your code

For any feature, ask four questions. Writing the answers down is a basic threat model, and even a scrappy one finds real bugs.

  1. What are we protecting? Passwords, personal data, marks, money, the ability to post as someone else.
  2. Who might want it? A curious classmate, an automated scanner, a bored user, someone with a grudge. You do not need spies in your model; the automated scanner is enough to motivate every control in this book.
  3. Where does untrusted data enter? List every input, including ones you did not design: headers, cookies, file names, image metadata.
  4. What happens if each input is hostile? Go one at a time, and assume the worst plausible value.

A worked example

A class project: students upload a profile photo and the site shows it on a public page. Four inputs: the file itself, its name, its size, and the logged-in user ID the upload is recorded against.

Five controls, from one feature, in about ten minutes. Compare that with finding the same five in production.

CIA, and why availability counts

Security is usually split three ways: confidentiality (only the right people can read it), integrity (only the right people can change it, and you can tell if they did) and availability (it works when needed). Students tend to focus on the first. A marking system that loses an assignment has an integrity failure; one that falls over on the due date has an availability failure. Both are security problems.

Staying legal while you learn

This is not a footnote. Testing a system you do not own, or do not have written permission to test, is a criminal offence in Canada and nearly everywhere else, however harmless your intent and however obvious the bug. "I was only looking" is not a defence, and a student record is easy to ruin.

Practise on things built for it: your own applications, deliberately vulnerable apps you run locally such as OWASP Juice Shop, capture-the-flag competitions, and bug bounty programmes, strictly inside their published scope. Chapter 12 covers this properly. Everything in this book can be learned entirely on your own machine.

Exercises

1. Map your own boundaries

Take a project you have written, even a small one, and list every place data enters it. For each, write who controls that data.

Show answer

A typical list for a beginner web app: form fields and URL parameters (the user), cookies and headers (the user, including ones your framework sets), uploaded files (the user), a third-party API response (that company, plus anyone who can intercept an unencrypted connection), a config file or environment variable (you, unless the server is shared), and command-line arguments (whoever starts the program).

The useful surprise for most people is how much of it the user controls. Cookies and headers are sent by the browser, so they are user input too, even though you wrote the code that sets them.

2. Find the trusted input

What is wrong with this Flask route, and what would you change?

@app.route("/profile")
def profile():
    user_id = request.args.get("user_id")
    user = db.get_user(user_id)
    return render_template("profile.html", user=user)
Show answer

The user ID comes from the query string, so visiting /profile?user_id=2 shows somebody else's profile. This is a broken access control bug, specifically an insecure direct object reference, and it is one of the most common findings in real web applications because the code looks perfectly reasonable.

@app.route("/profile")
@login_required
def profile():
    user = db.get_user(session["user_id"])   # identity from the session
    return render_template("profile.html", user=user)

Identity comes from the session, never from the request. If a route genuinely needs to show another user's page, it must check that the logged-in user is allowed to see it — on the server, on every request.

3. Read this month's attacks

Open the Cyber Brief and look at the entries added in the last month. Group them by weakness type. Which three types appear most?

Show answer

The exact answer changes every month, which is the point of doing it on live data rather than reading a fixed list here. Across 2026 the most common weaknesses in that catalogue have been code and command injection, authentication bypass, and path traversal, with memory-safety bugs close behind.

All three of the leaders are covered in this book, and all three come down to the same sentence: data from outside was used as an instruction. If the exercise makes that feel repetitive, it has worked.
