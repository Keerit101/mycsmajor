Security basics for programmers · Chapter 2

Passwords done properly

Storing a password is a solved problem that student projects keep getting wrong. The correct version is about five lines long, and understanding why it looks like that teaches you most of applied cryptography.

Start from the assumption that your database leaks

Design as if an attacker will one day get a copy of your user table: through SQL injection, a stolen backup, a misconfigured cloud bucket or a laptop left on a train. All of those happen regularly. The question is not whether you can prevent it with certainty, but how much damage the copy does.

If passwords are stored as text, the damage is enormous, and not only to your site. People reuse passwords, so your leak becomes a break-in at their email, which is the master key to everything else.

Hashing, and why it is not enough on its own

A cryptographic hash turns input into a fixed-size value, cannot be reversed, and changes completely if the input changes at all.

import hashlib
print(hashlib.sha256(b"password").hexdigest())
# 5e884898da28047151d0e56f8dc6292773603d0d6aabbdd62a11ef721d1542d8

You store the hash, and at login you hash what was typed and compare. The password itself is never kept. So far so good — and still broken, for two reasons.

Reason one: identical passwords give identical hashes. That hash of password is the same on every site in the world. Attackers keep precomputed tables of hashes for billions of common passwords, so a lookup, not a calculation, recovers it instantly. The line above appears in those tables.

Reason two: SHA-256 is designed to be fast. Fast is exactly what you do not want here. A single modern GPU can try billions of SHA-256 guesses per second, so the whole dictionary falls in minutes.

Salt fixes the first problem

A salt is random data, unique per user, stored alongside the hash and mixed in before hashing. It is not a secret; its job is to make every stored hash different even when two users chose the same password. That breaks precomputed tables, because the attacker would need a separate table per salt.

Generate it with a cryptographically secure source, never with random:

import os
salt = os.urandom(16)      # 16 random bytes, unique per user

Python's random module is predictable by design and must never be used for anything security-related. Use os.urandom or the secrets module (secrets.token_hex(16)) instead.

Slowness fixes the second

A password hashing function is deliberately expensive: it repeats work many times, and the good ones also demand a lot of memory, which makes custom cracking hardware far less effective. Four acceptable choices today:

FunctionUse when
Argon2idfirst choice for new code; memory-hard and current
scryptalso memory-hard, available in Python's standard library
bcryptwell understood, everywhere; note its 72-byte input limit
PBKDF2when you cannot install anything: in the standard library, acceptable with a high iteration count

Anything else — MD5, SHA-1, SHA-256, SHA-512 on its own, or your own scheme of hashing twice with some text mixed in — is wrong for passwords. Not "old fashioned": wrong.

The whole thing, in the standard library

PBKDF2 with SHA-256, no packages needed:

import hashlib, os, hmac

ITERATIONS = 600_000      # OWASP's current floor for PBKDF2-HMAC-SHA256

def hash_password(password: str) -> tuple[bytes, bytes]:
    salt = os.urandom(16)
    key = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, ITERATIONS)
    return salt, key      # store BOTH, plus the iteration count

def verify(password: str, salt: bytes, expected: bytes) -> bool:
    key = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, ITERATIONS)
    return hmac.compare_digest(key, expected)

Three details that are easy to miss:

  • Store the iteration count with each hash. Hardware gets faster, so you will raise it, and old rows must still verify. Many libraries pack algorithm, cost, salt and hash into one string for exactly this reason.
  • hmac.compare_digest, not ==. A normal comparison stops at the first differing byte, so how long it takes leaks how much of the value was right. That is a timing attack, and the fix is a comparison that always takes the same time.
  • The salt is not secret and goes in the same table. Only the password is a secret, and you never have it.

On the machine these pages were written on, 600,000 iterations took about 0.15 seconds. That is unnoticeable at a login and ruinous for an attacker trying a billion guesses. Tune the cost so a login takes a few hundred milliseconds on your real server.

If you can install a package

from argon2 import PasswordHasher       # pip install argon2-cffi
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher()
stored = ph.hash("correct horse battery staple")   # salt is inside the string

try:
    ph.verify(stored, typed_password)
    if ph.check_needs_rehash(stored):              # parameters have moved on
        stored = ph.hash(typed_password)
except VerifyMismatchError:
    pass   # wrong password

This is the version to prefer in real projects: the salt, the algorithm and the cost parameters all live inside the stored string, and the library upgrades them for you. Better still, use whatever your web framework already provides — Django's make_password, Rails' has_secure_password — because it is maintained by people who follow this subject full time.

The rest of the login

Hashing is necessary, not sufficient. The same page needs:

  • One error message. "Wrong email or password", never "no such user", which otherwise tells an attacker which addresses are registered.
  • Rate limiting. Slow down or lock out after repeated failures, per account and per IP address. Without this, an attacker does not need your database at all.
  • Length over complexity. Require at least 8 characters, allow very long ones, allow spaces and symbols, and do not force mixtures or expiry. Modern guidance (NIST SP 800-63B) says those rules push people towards Password1! and annual increments.
  • A check against known-breached passwords, for example Have I Been Pwned's range API, which lets you check without sending the password.
  • HTTPS everywhere. Careful hashing is pointless if the password crosses the network in the clear.
  • Never log it. Debug logging of request bodies is a classic way for plaintext passwords to end up in a file anyone can read.

Exercises

1. Find every mistake

How many things are wrong here?

import hashlib, random

def register(username, password):
    salt = str(random.randint(1000, 9999))
    digest = hashlib.md5((password + salt).encode()).hexdigest()
    db.execute(f"INSERT INTO users VALUES ('{username}', '{digest}', '{salt}')")
    print(f"registered {username} with password {password}")
Show answer

Six, at least:

  1. MD5 is broken and far too fast for passwords.
  2. random is predictable; use os.urandom or secrets.
  3. A four-digit salt has only 9,000 values, so one set of tables covers them all. Use at least 16 bytes.
  4. No iteration count or cost parameter: a single pass of a fast hash.
  5. SQL injection: the username is pasted into the query. A username of ', '', '') -- rewrites it. Use parameters.
  6. The password is printed, so it lands in the logs in plain text.

Every one of these has appeared in a real breach report.

2. Measure the cost

Time pbkdf2_hmac with 1,000, 100,000 and 600,000 iterations, then work out how many guesses per second an attacker with a thousand times your hardware would manage at each setting.

Show answer 
import hashlib, os, time

for iters in (1_000, 100_000, 600_000):
    salt = os.urandom(16)
    start = time.perf_counter()
    hashlib.pbkdf2_hmac("sha256", b"hunter2", salt, iters)
    elapsed = time.perf_counter() - start
    print(f"{iters:>7} iterations: {elapsed*1000:6.1f} ms -> {1/elapsed:,.0f} guesses/sec")

The time scales almost exactly with the iteration count, which is the whole design. Suppose 600,000 iterations takes 0.15 s, so about 7 guesses per second for you; an attacker a thousand times faster manages roughly 7,000 per second. A six-character lower-case password is about 300 million combinations, which at that rate takes over a year rather than the few seconds an unsalted SHA-256 would need.

This is also the argument for length: every extra character multiplies the work, while raising the iteration count only doubles it.

3. Write the login

Using the hash_password and verify functions above, write login(email, password) that returns True or False and leaks nothing about which emails exist.

Show answer 
DUMMY_SALT = os.urandom(16)
DUMMY_HASH = hashlib.pbkdf2_hmac("sha256", b"not a real password", DUMMY_SALT, ITERATIONS)

def login(email: str, password: str) -> bool:
    row = db.get_user_by_email(email)              # parameterised query
    if row is None:
        verify(password, DUMMY_SALT, DUMMY_HASH)   # same work either way
        return False
    return verify(password, row.salt, row.password_hash)

Hashing against a dummy value for unknown emails keeps the response time the same whether or not the account exists. Without it, a missing account answers in microseconds and a real one in 150 milliseconds, and that difference is enough to enumerate your users. Pair it with one generic error message and rate limiting, and the login page is in reasonable shape.
