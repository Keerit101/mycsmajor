Git, Linux and the terminal · Chapter 2

Git without panic

Git is frightening because its messages are written for people who already understand it. Learn the model first and the commands stop being magic spells.

The model: three places your work can be

  working directory  ──git add──▶  staging area  ──git commit──▶  repository
  (your files, as                 (what will go in                (permanent
   they are now)                   the next commit)                 history)

Most confusion comes from the middle box. Editing a file changes the working directory only. git add copies the current state of that file into the staging area. git commit turns whatever is staged into a permanent snapshot. Edit the file again after staging and you now have two versions in play, which is exactly what git status is telling you when it lists the same file twice.

A commit is a full snapshot of the project plus a message, an author and a pointer to its parent. A branch is just a movable label pointing at one commit. That is the entire data model.

Starting out

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

git init                       # start a repository in this folder
git clone <url>                # or copy an existing one

Set the name and email before your first commit; they are recorded in every commit and are tedious to change afterwards.

The daily loop

git status                     # what has changed, and what is staged
git diff                        # changes not yet staged
git diff --staged               # changes that are staged
git add main.py                 # stage one file
git add .                       # stage everything here and below
git commit -m "Add input validation to the parser"
git log --oneline -10           # the last ten commits

Run git status constantly. It is not just a report: it names the command for whatever you probably want to do next. Reading it carefully solves most Git problems before they become problems.

On messages: say what the commit does, in the imperative, in one line under about 70 characters. "Fix off-by-one in the loop bound" is useful in six months; "stuff", "fix", "asdf" and "final final v2" are not. Commit when a piece of work makes sense on its own, not once a day.

Branches

git switch -c feature-login     # create a branch and move onto it
git switch main                 # back to main
git branch                      # list branches, * marks the current one
git merge feature-login         # bring that branch's work into this one
git branch -d feature-login     # delete it once merged

switch and restore are the modern commands; older material uses git checkout for both jobs, which is part of why it felt confusing. Both still work.

Work on a branch whenever you are trying something you might abandon. If it fails, delete the branch and nothing was lost. That is the point.

Working with GitHub

git remote -v                   # where "origin" points
git push -u origin main         # push and remember the link (first time)
git push                        # after that
git pull                        # fetch and merge others' work
git fetch                       # fetch without merging, to look first

Pull before you start work and push when you finish, every session. Most merge pain is the result of a branch that sat untouched for two weeks.

What to do when Git says something frightening

"Your branch and 'origin/main' have diverged"

You committed locally and someone else pushed. Bring their work in and put yours on top:

git pull --rebase

This replays your commits after theirs, giving one straight line instead of a merge commit. Safe while your commits are still only on your machine.

A merge conflict

Git stops and marks the clashing region in the file:

<<<<<<< HEAD
total = price * 1.13
=======
total = price * TAX_RATE
>>>>>>> feature-tax

Above the ======= is your side, below it is theirs. Edit the file into what it should actually be, delete all three marker lines, then:

git add the-file.py
git commit                      # finishes the merge

Nothing is broken and nothing is lost. A conflict only means two people changed the same lines, and Git is sensibly refusing to guess. To abandon the attempt entirely, git merge --abort puts everything back.

"detached HEAD"

You checked out a commit rather than a branch, so new commits would have no label and would be hard to find later. If you have not committed anything, git switch main fixes it. If you have, git switch -c rescue-branch keeps that work by giving it a name.

I committed something I should not have

git restore main.py                 # discard unstaged changes to a file
git restore --staged main.py        # unstage, keep the edits
git commit --amend -m "Better message"   # fix the last commit (not pushed yet)
git revert <hash>                   # undo a pushed commit with a new commit
git reset --soft HEAD~1             # undo the last commit, keep the changes staged

Use revert for anything already pushed: it adds a commit that undoes the change, so nobody else's history breaks. Keep reset for commits that are still local, and be careful with --hard, which throws your edits away with no copy anywhere.

One serious exception: if you committed a password or an API key, removing the commit is not enough, because it still exists in the history and in every clone. Treat the secret as leaked, revoke it immediately, then clean the history. Add the file to .gitignore and keep secrets in environment variables so it cannot happen twice.

I have genuinely lost a commit

git reflog

This lists everywhere HEAD has been for the last 90 days, including commits that no branch points at any more. Find the hash and git switch -c rescue <hash>. Git almost never deletes a commit you made; it loses the label. Knowing reflog exists is what turns Git from frightening into merely fiddly.

.gitignore

# Python
__pycache__/
*.pyc
.venv/

# Node
node_modules/

# Editors and systems
.vscode/
.DS_Store

# Secrets
.env

Commit this file first, before anything else. Once node_modules or a .env is in the history, getting it out is real work. github/gitignore has a ready-made file for every language.

Exercises

1. The staging area, proved

Create a file, stage it, then edit it again without staging. Run git status, git diff and git diff --staged. Explain what each shows.

Show answer

git status lists the file twice: once under "Changes to be committed" and once under "Changes not staged for commit". Both are true — the staged version and the current version differ.

git diff shows only the second edit, the difference between the staging area and your working file. git diff --staged shows the first version, the difference between the last commit and the staging area.

If you commit now, only the staged version is recorded. This is the mechanism behind git add -p, which lets you stage some of your changes and leave the rest for another commit.

2. Cause a conflict and fix it

On a branch, change line 1 of a file and commit. On main, change the same line differently and commit. Merge. Resolve it.

Show answer 
git switch -c experiment
# edit line 1
git commit -am "Change the greeting on the branch"
git switch main
# edit line 1 differently
git commit -am "Change the greeting on main"
git merge experiment            # CONFLICT
# edit the file: keep what you actually want, delete the <<< === >>> lines
git add the-file.txt
git commit

Doing this once on purpose, on a throwaway repository, is worth more than reading about it ten times. The mystery disappears, and you will not panic when it happens the night before a deadline.

3. Rescue a lost commit

Commit some work on a branch, switch to main, delete the branch with git branch -D, then get the commit back.

Show answer 
git reflog                      # find the line for your commit
git switch -c recovered <hash>  # give it a label again
git log --oneline -3            # confirm the work is there

The commit was never deleted. git branch -D only removed the label pointing at it, leaving it unreachable but still stored, and Git keeps unreachable commits for about 90 days before garbage collection.

So the honest summary of Git safety is: once you have committed, your work is very hard to actually lose. Work that was never committed has no such protection, which is the real argument for committing often.
